# Project meta-review — October 5, 2026

## Overall assessment

The project has a sound architecture and is substantially healthier after the
previous review, but some documented guarantees are stronger than the
implementation and tests establish. The next improvements should focus on
invariants, concurrency, and verification rather than another architectural
rewrite.

The single Next.js application is appropriate for the project's size. Explicit
API allowlists, owner-scoped writes, purpose-bound and atomically consumed reset
tokens, pure calculator functions, and input-only persistence provide good
foundations. The code is readable and consistently structured. The ADRs and
deployment runbook preserve useful context.

## Findings

### AUTH-01 — Password mutation guarantees are not atomic

**Priority:** High

**Locations:** `src/app/api/user/set-password/route.ts:18–40`,
`src/app/api/user/change-password/route.ts:18–46`.

Both routes inspect the authenticated user, perform asynchronous password
hashing, then update by user ID alone. The authorization and credential-state
preconditions are not checked again in the write.

This creates two races:

- Two initial-password requests can both observe no password and then overwrite
  each other, despite the rule that setting an initial password must never
  overwrite an existing one.
- A change-password request can validate the old password, overlap a password
  reset, and then overwrite the newly reset password. It also receives a fresh
  session after that write.

The `$inc` prevents lost session-version increments, but it does not make the
authorization check and credential write one operation.

**Recommended fix:** Use conditional updates that match the expected session
version and credential state. Return a conflict or authentication failure when
those preconditions have changed. Preserve the session-revocation behavior in
ADR-002 and authenticated initial-password behavior in ADR-001.

**Acceptance criteria:**

- Concurrent initial-password requests cannot overwrite the winning password.
- A password change authorized against stale credentials cannot overwrite a
  completed reset or another credential change.
- A failed conditional write does not mint a refreshed session.
- Successful changes continue to revoke earlier sessions and refresh the
  successful caller's session where intended.
- Regression coverage includes deliberately overlapping requests, particularly
  password change versus reset.

**Resolution (October 5, 2026):** `set-password` now writes with
`User.findOneAndUpdate` filtered on the observed session version and
`password: { $in: [null, ""] }`; `change-password` filters on the observed
session version and the exact stored hash it compared against. Both return
409 when the filter no longer matches, and the refreshed session cookie is
minted only after a successful write. Verification: unit tests assert the
write filters and that conflicts do not call `signToken`/`setAuthCookie`;
database-backed tests deliberately overlap two initial-password requests, two
changes with the same old password, and a completed reset followed by a
stale change, then verify the persisted hash, a single session-version bump,
and one minted session (`npm test`: 226 passed; `npm run test:integration`:
11 passed). No known limitation.

### CALC-01 — Field validation does not enforce mixture invariants

**Priority:** High

**Locations:** `src/lib/validation.ts:92–99`,
`src/lib/calculator.ts:197–259`, `src/lib/calculator.ts:118–157`,
`src/lib/helpers.ts:7–8,58–64`.

PG and VG are individually range-checked, but their sum is not validated. This
affects recipe/settings API inputs and restored calculator drafts.

**Reproduced:** A version-2 draft with target PG/VG `80/80`, zero target
nicotine, no flavors, and a target volume of 30 mL is accepted. The calculator
produces 24 mL PG plus 24 mL VG with an empty error string: **48 mL of
instructions for a 30 mL target**. The recipe parser also accepts
`{ base: { pg: 80, vg: 80 } }`.

There is a separate non-finite-value gap. Calling
`roundToTwoDecimalPlaces(1e-7)` returns `NaN` because the exponent-string
rounding implementation receives a number already represented in scientific
notation. Using that result as the target amount produces `NaN` weights, but
calculator status reports no error. `isResultsInvalid` only checks negativity.

**Recommended fix:** Define shared domain invariants for finite inputs/results,
normalized carrier ratios, and consistent ingredient totals. Enforce them at
API and draft boundaries and in calculator status. Validate partial recipe
updates against the merged document rather than just the supplied fields.
Use an explicit numeric tolerance where floating-point arithmetic requires it.

**Acceptance criteria:**

- Invalid PG/VG sums cannot silently produce valid-looking instructions through
  stored drafts, recipes, or saved defaults.
- Non-finite inputs or results produce an invalid status and disable saving.
- Rounding supports small and large scientific-notation values within the
  supported numeric domain without unexpectedly producing `NaN`.
- Valid mixtures conserve the target volume within a defined tolerance.
- API create/update and draft restoration have regression coverage for the
  reproduced failures, including partial-update behavior.

**Resolution (October 5, 2026):** A shared `isNormalizedRatio` invariant
(finite, 0–100, sum within a 0.01 tolerance) is enforced in three places:
`parseRatio` rejects non-normalized recipe/settings payloads (including
partial recipe updates, which carry complete ratio objects);
`parseCalculatorDraft` drops non-normalized target pairs, nicotine configs,
and flavor entries; and `getCalculatorStatus` marks ratio-invalid and
non-finite results invalid so Save is disabled. `roundToTwoDecimalPlaces` now
handles scientific notation (`1e-7` → `0`, values at or above
`Number.MAX_SAFE_INTEGER` pass through) and `isResultsInvalid` rejects
non-finite values. Verification: the reproduced 80/80 draft is covered in
`calculator.test.ts`; route tests cover create, update, and settings
rejection; a conservation test asserts ingredient totals equal the target
volume for valid mixtures. Limitation: existing stored documents with
non-normalized ratios are not migrated; they load with an explicit error and
cannot be saved until corrected.

### STATE-01 — Settings loading can become permanently cancelled

**Priority:** Medium

**Location:** `src/components/calculator/useCalculator.ts:182–220`.

The hook marks an account as loaded before its settings request completes. The
effect depends on the entire `user` object.

If authentication refresh supplies a new object for the same account while
settings are pending:

1. Effect cleanup cancels the original request's result.
2. The replacement effect sees that account already marked as loaded.
3. It skips fetching again.

**Reproduced:** Render the hook for `user-1` with a deferred settings response,
replace the auth user with a new object having the same ID, rerender, then
resolve settings specifying a target amount of 50 mL. Only one request is made;
the calculator stays at 30 mL and `hasSavedDefaults` remains false.

The saved-settings reference also survives logout, so previously loaded
account defaults remain available in the mounted calculator.

**Recommended fix:** Track requests by stable account ID, distinguish pending
from successfully loaded, and clear account-specific settings when identity
changes. Preserve active inputs and the initialization precedence in ADR-012.

**Acceptance criteria:**

- A same-account auth refresh during loading does not permanently discard
  settings.
- Failed or cancelled requests do not incorrectly mark settings as loaded.
- Logout/account switching clears the previous account's saved-defaults
  availability and flavor defaults without silently replacing active inputs.
- A late response for an earlier account cannot apply to the current account.
- Tests cover pending refresh, failure/retry, logout, and account switching.

**Resolution (October 5, 2026):** The hook records an account as loaded only
after its request succeeds, so a same-account auth refresh during a pending
request starts a replacement request instead of skipping it; failed requests
stay retryable. `hasSavedDefaults` is derived by comparing the loaded account
ID with the signed-in account, and the saved-settings ref is keyed by account
ID, so logout or an account switch stops offering/applying the old defaults
and stops inheriting flavor defaults without touching active inputs. Late
responses are cancelled per effect run. Verification: five new component
tests cover the pending same-account refresh, failure/retry, a late response
for a previous account, logout, and account switching
(`CalculatorAuth.test.tsx`, 14 tests passing). No known limitation.

### AUTH-02 — Twitter identity matching is weaker than Google's

**Priority:** Medium

**Locations:** `src/app/api/auth/twitter/callback/route.ts:61–84`,
`src/lib/models/user.ts:38–49`.

Twitter uses a single `$or` lookup for provider ID or email. If the provider ID
matches one account and the current email matches another, either document can
satisfy the query. The subsequent save assigns the Twitter identity to the
returned account.

Google explicitly prioritizes the immutable provider ID. Neither provider-ID
field has a unique index, so database constraints do not prevent duplicate
identity links.

**Recommended fix:** Resolve Twitter by immutable ID first. Handle email-based
linking separately with explicit conflict checks. Consider unique partial
indexes for provider IDs after inspecting existing data; account for the empty
strings currently written during unlinking. Record any extension to the
provider-linking rules in ADR-004.

**Acceptance criteria:**

- An established Twitter link deterministically resolves to its existing
  account even when the provider email matches a different account.
- A conflict cannot silently move or duplicate a provider identity.
- Concurrent linking behavior is defined and verified.
- Provider-ID constraints, if introduced, allow unlinked accounts and have an
  explicit existing-data inspection/index rollout procedure.
- Twitter callback regression coverage includes established links, email-based
  linking, and identity conflicts.

**Resolution (October 5, 2026):** The callback now resolves established links
by the immutable `twitterId` first, then falls back to email. An email match
whose account already carries a different Twitter identity is refused with
`authError=twitter-conflict` (message added to `AuthErrorNotice`), and
claiming an unlinked account uses a conditional update whose filter only
matches an absent, empty, or identical provider ID, so simultaneous claims
cannot both win. Verification: a new callback unit suite covers established
links, email linking, conflicts, concurrent-claim loss, account creation, and
token mismatch; database-backed tests cover ID-first resolution over a
conflicting email, conflict preservation, and a two-identity claim race with
exactly one winner. Unique partial indexes on `googleId`/`twitterId` now
enforce one account per non-empty provider ID (unlinked accounts, which store
an empty string or omit the field, remain unconstrained). Staging and
production were audited clean with `scripts/inspect-duplicates.mjs` on
October 5, 2026 before the indexes were added, and the production audit was
repeated against the restored backup. Database-backed tests cover
duplicate-key rejection and unlinked coexistence; `docs/deployment.md` keeps
the audit as the pre-rollout check for restored or migrated data.

### DATA-01 — Account deletion can race with dependent writes

**Priority:** Medium

**Locations:** `src/app/api/user/route.ts:72–81`,
`src/app/api/recipes/route.ts:31–55`, `src/app/api/settings/route.ts:23–50`.

Deleting dependent records before the user improves retryability, but it does
not guarantee removal of all owned data under concurrency.

A recipe creation or settings save can authenticate before deletion, then
insert after dependent cleanup. The account deletion succeeds while leaving
an orphan. This is narrower than the successful-deletion guarantee in ADR-010.

**Recommended fix:** Coordinate deletion and dependent writes through a shared
deletion-state or transactional protocol. The protocol must cover both
deletion and creation; merely wrapping deletion in a transaction is
insufficient.

**Acceptance criteria:**

- Overlapping recipe creation/settings upsert and account deletion cannot
  leave dependent records for a successfully deleted account.
- Failure behavior remains recoverable and is documented.
- Tests deliberately overlap deletion with both dependent-write paths and
  inspect the final database state.
- ADR-010 describes the actual coordination and retry guarantees.

**Resolution (October 5, 2026):** Deletion now marks the user document with
`deleting: true` before removing dependents (idempotent, so a retry is safe),
and both dependent-write routes (`POST /api/recipes`, `POST /api/settings`)
re-check the account after writing through `accountAcceptingWrites`; when the
account is gone or deleting, they delete their own record and return 409.
Verification: unit tests assert the mark-before-cleanup order, compensation
calls, and that partial cleanup failure keeps the account; database-backed
tests overlap `DELETE /api/user` with recipe creation and verify zero
orphaned recipes/settings, and replay stale writes after a completed deletion
for both paths. ADR-010 was rewritten to describe the protocol and the
partial-failure behavior. Limitation: after a partial failure the account
remains with `deleting: true`; reads still work, writes are refused, and the
deletion can be retried.

## Review process and operational findings

### TEST-01 — Tests often verify mechanisms rather than guarantees

The suite has grown considerably and covers valuable regressions. However:

- Password tests mock database updates and assert `$inc` and cookie calls.
- Index tests establish schema declarations, not actual database enforcement.
- Browser tests primarily cover signed-out calculation, layout, and
  accessibility.
- No Twitter callback test was found.

These are useful tests, but they do not prove claims such as "never overwrites
an existing password" or "successful deletion removes all owned data."

**Recommended fix:** Add a small database-backed integration suite covering
credential races, duplicate writes, provider-identity conflicts, and
deletion/write overlap. Keep the fast unit/component suite.

**Acceptance criteria:** Tests verify final persisted state and relevant
authorization/session outcomes against an isolated database, with controlled
overlap where needed. Test setup, cleanup, database isolation, and execution
commands are documented. This item may be implemented alongside AUTH-01,
AUTH-02, and DATA-01 rather than as a separate test-only phase.

**Resolution (October 5, 2026):** Added `vitest.integration.config.mts` and
`npm run test:integration`. The suite uses `MONGODB_TEST_URI` when provided
(CI supplies a MongoDB service container) and otherwise starts
`mongodb-memory-server`. Each test file creates a uniquely named temporary
database, creates schema indexes before use, and drops the database on
completion; a `server-only` alias lets the real route modules, models, and
`accountAcceptingWrites` run while only the session/cookie layer and the
Twitter HTTP exchange are mocked. Verification: 11 database-backed tests pass
covering credential races, duplicate recipe/settings writes, provider
identity resolution/conflicts, and deletion/write overlap, inspecting final
persisted state and session outcomes. Setup, isolation, and commands are
documented in `README.md`, `docs/deployment.md`, and the config comment.

### DOC-01 — Review closure language is too absolute

The previous review's "all checklist items are resolved" statement and several
ADR consequences imply broader guarantees than were verified. The preceding
findings expose gaps in the claimed guarantees despite passing regression
tests and successful manual flows.

**Recommended fix:** Retain the ADRs, but distinguish intended invariants,
implemented mechanisms, automated evidence, manual verification, and remaining
limitations. Avoid treating implementation details as proven behavior.

**Acceptance criteria:** Affected ADRs and this review's resolution notes
accurately describe concurrency boundaries and verification evidence. Items
requiring external setup or verification are not marked resolved prematurely.

**Resolution (October 5, 2026):** ADR-001, ADR-002, ADR-004, ADR-010,
ADR-011, and ADR-012 now describe the implemented concurrency mechanisms and
their boundaries rather than implying broader guarantees. Each resolution
note above separates unit/component evidence from database-backed evidence
and states remaining limitations (legacy ratio data, provider-ID indexes,
deletion retry state). OPS-01 and OPS-02 remain unchecked with their
maintainer actions recorded below.

### OPS-01 — Deployment verification lacks a repository-enforced gate

No checked-in CI workflow was found, while pushes to `master` auto-deploy.
Validation currently depends on the maintainer following the documented
commands.

**Recommended fix:** Automate the existing validation commands before
deployment. Establish how their results gate changes to `master` or production
deployment; adding a workflow alone does not establish that gate.

**Acceptance criteria:** CI runs the project's required checks on the pinned
Node.js version, installs Firefox for the production-build browser suite, and
uses suitable test-only configuration. The actual merge/deployment gating
mechanism is configured and documented, or the remaining maintainer action is
explicitly recorded with this item left open. Do not require production
secrets or a production database to run the suite.

**Resolution (October 5, 2026):** `.github/workflows/ci.yml` runs lint,
typecheck, unit/component tests, database-backed integration tests (MongoDB
service container, test-only credentials), the production build, and the
Firefox smoke suite on Node 22 for pushes to any branch and pull requests to
`master`. The first run (37223109035) passed all steps. A repository branch
ruleset (`master validation`) is active: it blocks deletion and force pushes
and requires the `Validation` status check on `master`, with the
pull-request requirement deliberately disabled. Rulesets enforce required
checks on the branch itself, so a commit without a passing `Validation` run
is rejected by `master`; the maintainer workflow is branch push, green check,
then push or merge to `master`. This change was exercised through that
workflow, and Vercel deploys the resulting `master` push.

### OPS-02 — Backup and restore lack an operational procedure

`docs/deployment.md` notes that the Atlas tier has no automated backups, but
provides no backup/restore procedure.

**Recommended fix:** Document a practical backup-and-restore workflow,
including cadence, storage/access ownership, retention, and a restore check.
Agree external storage or scheduled infrastructure choices with the maintainer
where needed.

**Acceptance criteria:** The runbook gives executable backup and restore
instructions and records a successful restore check into an isolated database.
The intended cadence and responsible owner are explicit. Documentation alone
must not be described as an implemented automated backup system.

**Resolution (October 5, 2026):** `docs/deployment.md` documents the agreed
routine: weekly gzipped `mongodump` archives owned by the maintainer, stored
outside the repository on an encrypted disk, with eight-week retention. The
first restore check was performed on 2026-10-05: the production archive
restored 4 documents with 0 failures into an isolated database, the duplicate
audit was clean, and the temporary collections were dropped. The runbook's
table records the check, and the procedure is not described as automated.
