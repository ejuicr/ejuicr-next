# Project review — October 2026

Review date: October 4, 2026.

The rebuild has a good structural foundation, but this review found a critical
account-takeover vulnerability, missing API safeguards, and calculator bugs
that can lose drafts or display incomplete mixing instructions. Address these
alongside the visual issues identified through user testing.

No application source changes were made during the review. `docs/todo.md` was
left unchanged. The initial review ended with a clean Git working tree; this
report was subsequently added and updated with browser findings.

## Security and authentication findings

### SEC-01 — Signup allows takeover of OAuth-only accounts

**Priority:** Critical.

**Location:** `src/app/api/user/route.ts:29–41`.

When signup finds an existing account without a password, it sets the password
supplied by the requester and issues a session for that account. There is no
requirement to be signed in as that user or prove ownership of the email
address.

**Impact:** Someone who knows an OAuth-only user's email can access the account,
its recipes, and account-management actions.

This vulnerability was inherited from the original Express implementation.

**Recommended fix:**

- Public signup must reject existing accounts.
- Add a separate authenticated set-password operation that derives the account
  from the session.
- Keep email-based recovery behind password-reset verification.
- Update the login message suggesting signup as a way to add a password.

The legitimate My Account Set Password form also calls public signup, so its
caller must be updated with the endpoint.

**Resolved (October 4, 2026).** Public signup now rejects every existing
account instead of attaching a password to accounts created through OAuth.
The new authenticated `POST /api/user/set-password` endpoint derives the
account from the session, refuses to overwrite an existing password, and
hashes the new one; My Account's Set Password form calls it. The login message
now directs provider-only accounts to sign in with their provider and set a
password from My Account rather than suggesting public signup. README endpoint
documentation includes the new route.

Regression coverage:

- `src/app/api/user/__tests__/signup.test.ts` — existing provider-only and
  password accounts are rejected without writes, session issuance, or password
  changes; new signups still hash passwords and start a session.
- `src/app/api/user/__tests__/set-password.test.ts` — 401 without a session,
  hashed password set for the session account, refusal to overwrite an
  existing password, and invalid-password rejection.
- `src/app/api/user/login/__tests__/route.test.ts` — guidance names the
  provider and My Account and no longer suggests signup; password login and
  unknown-email behavior are unchanged.
- `src/components/account/__tests__/MyAccount.test.tsx` — the Set Password
  form posts to `/api/user/set-password`.

Validation: `npm run lint`, `npm run typecheck`, `npm test`, and
`npm run build` all pass.

### SEC-02 — Recipe and settings updates trust the entire request body

**Priority:** High.

**Locations:**

- `src/app/api/recipes/[id]/route.ts:45–47`.
- `src/app/api/settings/route.ts:34–38`.

Both handlers pass client-supplied objects directly to Mongoose update methods
without `runValidators`.

**Consequences:**

- Known internal fields such as recipe `author` and settings `user` can change.
- MongoDB update operators are accepted.
- Numeric limits, enums, and required-field rules can be bypassed on updates.
- Invalid documents can later break calculator or settings rendering.

Initial ownership checks do not make update payloads safe.

**Recommended fix:** Build allowlisted update objects, keep ownership immutable,
validate request shapes, and enable update validators. Prefer queries including
both document ID and current owner.

**Resolved (October 4, 2026).** `src/lib/validation.ts` now rebuilds recipe and
settings payloads field by field from untrusted JSON. Internal fields (`_id`,
`author`, `user`, timestamps) and MongoDB update operators are ignored, numeric
ranges and enums are enforced, and nested PG/VG and ingredient shapes are
required in full. Recipe updates use an owner-scoped
`{ _id, author }` query with `runValidators: true`; a recipe the caller cannot
edit returns 404 instead of disclosing that it exists. Settings updates enable
validators as well, and recipe/settings creation uses the same allowlisted
builders.

Regression coverage:

- `src/lib/__tests__/validation.test.ts` — builders ignore injected fields and
  operators and reject invalid types, enums, ranges, and partial nested shapes.
- `src/app/api/recipes/[id]/__tests__/update.test.ts` — owner-scoped filter,
  allowlisted payload, `runValidators`, and 404 for missing/foreign recipes.
- `src/app/api/recipes/__tests__/create.test.ts` — creation strips injected
  `_id`/author/`$set` and still enforces titles and shapes.
- `src/app/api/settings/__tests__/route.test.ts` — create and update paths use
  allowlisted payloads and reject invalid settings before writing.

### SEC-03 — Authentication inputs lack reliable server validation

**Priority:** High.

**Locations:**

- `src/app/api/user/route.ts:18–25`.
- `src/app/api/user/login/route.ts:13–20`.
- `src/lib/models/user.ts:12–21`.

Signup checks only that email and password are truthy. TypeScript assertions
do not validate incoming JSON. The schema's string `min`/`max` options do not
enforce string lengths as intended: the installed Mongoose accepted a document
with `email: "x"` and `password: "x"` under these rules.

**Impact:** Direct requests can create malformed accounts that the stricter UI
cannot use. Non-string values can reach queries and hashing functions.

**Recommended fix:** Share explicit server validators across signup, login,
set/change password, and reset password. Validate types before queries and
define consistent email normalization. Plan normalization of existing addresses
carefully to avoid collisions between historical accounts.

**Resolved (October 4, 2026).** `src/lib/validation.ts` provides shared
`requireEmail`, `requirePassword`, and `requireNonEmptyString` helpers now used
by signup, login, set-password, change-password, reset-password, and the reset
token route. Values are type-checked before queries or hashing, emails are
trimmed and format-validated, and new passwords enforce the 6–250 length
range. Login and current-password checks only require non-empty strings so
accounts created with legacy passwords keep working. New signup and password
creation store lowercase addresses (the user schema now also trims and
lowercases email). Lookups use `findUserByEmail`, which prefers an exact match
then falls back to the lowercase form, so existing mixed-case accounts are not
locked out; the schema's ineffective string `min`/`max` options were replaced
with `minLength`/`maxLength`.

Regression coverage:

- `src/app/api/user/__tests__/signup.test.ts`, `login/__tests__/route.test.ts`,
  `change-password.test.ts`, `set-password.test.ts`,
  `reset-password.test.ts`, and `reset-password-token.test.ts` — non-string,
  malformed, short, and long inputs return 400 before database access, while
  valid flows still hash and store passwords.
- `src/lib/__tests__/validation.test.ts` — validator edge cases and messages.
- `src/lib/__tests__/auth.test.ts` — exact-match preference and legacy
  lowercase fallback for `findUserByEmail`.

Validation: `npm run lint`, `npm run typecheck`, `npm test` (96 tests across
14 files), and `npm run build` all pass.

### SEC-04 — Password changes do not revoke sessions; reset links are reusable

**Priority:** High.

**Locations:**

- `src/lib/auth.ts:19–25`.
- `src/app/api/user/change-password/route.ts:31–37`.
- `src/app/api/user/reset-password/route.ts:27–31`.
- `src/app/api/user/reset-password/[token]/route.ts:44–55`.

Sessions last 30 days without a password/session version check. Changing or
resetting a password does not invalidate existing sessions. Reset tokens remain
usable until their one-hour expiry, including after a successful reset.

**Impact:** Resetting a password does not reliably remove an existing session
holder. A used reset link can change the password again.

**Recommended fix:** Add session invalidation through a version or timestamp.
Make reset tokens single-use with atomic consumption and validate an explicit
token purpose.

The rebuild handles invalid/expired reset tokens better than the old server,
but their lifecycle remains incomplete.

**Resolved (October 4, 2026).** Session tokens now carry a `purpose` and the
account's `sessionVersion`; `getCurrentUser` rejects a token whose version no
longer matches the account. Change-password, set-password, and reset-password
increment that version, revoking every previously issued session. The current
client receives a fresh cookie after change/set so it stays signed in while
other sessions are dropped. Reset links are signed with an explicit
`password-reset` purpose and a stored random nonce; the reset route consumes
the nonce with an atomic `findOneAndUpdate` filter, so a link cannot be
replayed, and requesting a new link supersedes earlier ones. Legacy session
tokens without a version keep working, while old reset links without a purpose
are rejected.

Regression coverage:

- `src/lib/__tests__/auth.test.ts` — token purpose/version signing, matching
  versions accepted, stale versions rejected, legacy sessions accepted, and
  non-session purposes rejected.
- `src/app/api/user/__tests__/change-password.test.ts` and
  `set-password.test.ts` — password hash stored, `sessionVersion` incremented,
  and a fresh cookie issued.
- `src/app/api/user/__tests__/reset-password.test.ts` — nonce stored and
  embedded in a purpose-bound link.
- `src/app/api/user/__tests__/reset-password-token.test.ts` — purpose
  enforcement, atomic nonce consumption, session revocation, and replay
  rejection.

Validation: `npm run lint`, `npm run typecheck`, `npm test` (103 tests across
14 files), and `npm run build` all pass.

### SEC-05 — Google links by email without checking verification

**Priority:** High.

**Locations:**

- `src/app/api/auth/google/callback/route.ts:47–73`.
- `src/lib/oauth/google.ts:12–17`.

The callback matches by Google identity or email, then attaches that identity
to the matched account. It checks only email presence; the profile type omits
`email_verified`.

**Impact:** Automatic linking assumes a provider-returned email proves ownership
of an existing local account. Google distinguishes email presence, verification,
and whether Google is authoritative for an address. A live provider exploit
was not demonstrated during this review.

**Recommended fix:** Look up established links by provider ID first. Require
appropriate verified-email guarantees or explicit ownership proof before
attaching a new provider to an existing account.

Reference: [Google OpenID Connect documentation](https://developers.google.com/identity/openid-connect/openid-connect).

**Resolved (October 4, 2026).** The callback now looks up established links by
Google's immutable `sub` first and signs them in without depending on email.
For any new link or account, it requires Google's `email_verified` claim to be
true; an unverified address is rejected with a new `google-email-unverified`
notice instead of attaching to an existing account or keying a new one. The
profile fetch also validates that `sub` is present and exposes
`emailVerified` explicitly. Regression tests cover established-link sign-in,
verified linking, unverified refusal, new-account creation, and state
mismatch.

### SEC-06 — Public authentication endpoints lack abuse protection

**Priority:** Medium–high.

**Locations:** Signup, login, and password-reset routes under `src/app/api/user/`.

There is no application-level rate limiting. Login responses distinguish
nonexistent accounts, incorrect passwords, and OAuth-only accounts.

**Impact:** Password guessing, account enumeration, reset-email spam, and
avoidable hashing/database load.

**Recommended fix:** Use rate limits that work across Vercel instances, with
controls by requester and account identifier. Use generic public
authentication/recovery responses where practical.

**Decision (October 4, 2026):** implement in-app best-effort rate limiting
(per-instance memory buckets) rather than an external store. This limits
abuse per instance but is not a global cap under horizontal scaling.
Implementation pending.

**Resolved (October 4, 2026).** Authentication routes now apply in-process
fixed-window limits keyed by requester IP and account identifier: signup
(10/15 min per IP, 3/15 min per email), login (20/15 min per IP, 10/15 min per
email), and password reset (10/15 min per IP, 3/15 min per email). Limits
throw 429 with a `Retry-After` header. Password-reset requests return the same
generic message whether or not the account exists, so the endpoint can no
longer be used to discover addresses. Login keeps the provider-specific
guidance required by SEC-01, and signup keeps its explicit "User already
exists." message; the rate limits mitigate enumeration abuse. Buckets are per
instance (best-effort, as decided); a distributed store would be needed for a
global cap. Regression tests cover the limiter, key isolation, window resets,
IP parsing, and 429 responses through signup, login, and reset.

### SEC-07 — Last-sign-in-method protection exists only in the UI

**Priority:** Medium.

**Locations:**

- `src/components/account/MyAccount.tsx:404–451`.
- `src/app/api/user/google/route.ts`.
- `src/app/api/user/twitter/route.ts`.

The UI checks whether another login method remains. The API handlers do not.

**Impact:** Direct requests can leave an account with neither a password nor a
linked provider, forcing recovery.

**Recommended fix:** Enforce the rule server-side and account for simultaneous
unlink requests.

**Resolved (October 4, 2026).** The Google and Twitter unlink handlers now use
an atomic conditional update whose filter requires another sign-in method
(password or the other provider) to remain. Two simultaneous unlink requests
cannot both succeed, and a rejected unlink returns 400 with guidance to set a
password. Regression tests verify the ownership filters, both providers, and
the refusal path.

### SEC-08 — Accepted password lengths exceed bcrypt's effective limit

**Priority:** Medium.

**Locations:** `src/lib/helpers.ts:80–85` and password handlers.

The application accepts up to 250 characters, but bcrypt uses only the first
72 bytes. Two different passwords sharing the same 72-byte prefix both matched
the same hash in an installed-library check.

**Recommended fix:** Enforce an explicit UTF-8 byte limit or adopt a hashing
strategy that supports the advertised length. Account for existing hashes
when changing the policy.

**Resolved (October 4, 2026).** New and changed passwords are limited to 72
UTF-8 bytes (`PASSWORD_MAX_BYTES`, counted by `passwordByteLength`) on both
the client (`validatePassword`) and the server (`requirePassword`), matching
bcrypt's effective hash length. Login only requires a non-empty string, so
existing accounts whose passwords exceed 72 bytes can still sign in and then
change to an accepted password. Regression tests cover ASCII and multibyte
boundaries at 72/73 bytes.

## Calculator findings

### CALC-01 — Zero-nicotine mode hides active nicotine calculations

**Priority:** High.

**Locations:**

- `src/components/calculator/useCalculator.ts:164–168, 203–241`.
- `src/components/calculator/Ingredients.tsx:110–131`.
- `src/components/calculator/TargetEjuice.tsx:64–90`.

When opening a saved recipe, settings can enable zero-nicotine mode. Nicotine
controls and the ingredient row disappear while nicotine strength and volume
remain active in calculations.

**Reproduced example:** A 30 mL recipe at 6 mg/mL using 100 mg/mL stock has
1.8 mL hidden nicotine. Visible ingredients total 28.2 mL, while the target
remains 30 mL. The visible instructions are incomplete.

**Recommended fix:** Define consistent behavior for saved recipes: preserve
the recipe's nicotine and show it, or explicitly convert the calculation to
zero nicotine. Never hide an active ingredient.

This behavior also exists in the original front end.

**Resolved (October 4, 2026).** Calculator visibility is now derived from
whether nicotine is actually active: the hook exposes `showNicotine`
(`!zeroNicotineMode || targetNicStrength > 0`) and both the Strength control
and the nicotine ingredient row use it, so an active ingredient can never be
hidden. When a saved recipe is opened, zero-nicotine mode is also initialized
from the recipe's own strength rather than the user's defaults.

### CALC-02 — Signing in overwrites the draft being saved

**Priority:** High.

**Location:** `src/components/calculator/useCalculator.ts:150–191`.

When authentication becomes available, settings replace all calculator inputs,
including flavors.

**Reproduced:** A guest draft with a custom flavor name and 50 mL target became
saved defaults — Flavor 1 and 30 mL — after sign-in. Settings can also overwrite
edits made while loading.

**Recommended fix:** Establish initialization precedence:

1. Explicitly opened recipe.
2. Existing or actively edited draft.
3. User defaults.
4. Application defaults.

Defaults should initialize fresh calculators. Provide a deliberate New Recipe
or Apply Defaults action rather than replacing an active draft.

**Resolved (October 4, 2026).** The calculator follows the documented
precedence: a saved recipe always wins; a draft restored from storage or edits
made while settings load block defaults; saved defaults initialize only a
fresh calculator; application defaults are the starting state. Settings still
supply display preferences (`units`). A deliberate **Apply Saved Defaults**
action was added for signed-in users with saved settings, so defaults remain
reachable without ever replacing a draft implicitly. The button is hidden
while viewing a saved recipe.

Regression coverage: `src/components/calculator/__tests__/CalculatorAuth.test.tsx`
verifies the zero-nicotine recipe case, fresh initialization from defaults,
draft preservation across sign-in/settings loading, preservation of edits made
while loading, the explicit Apply Saved Defaults action, and signed-out
behavior.

### CALC-03 — Intermediate calculations round too early

**Priority:** Medium.

**Location:** `src/components/calculator/useCalculator.ts:56–69, 211–219`.

Volumes are rounded before percentages, carrier contributions, and weights
are calculated.

**Reproduced example:** For a 0.1 mL target at 6 mg/mL using 100 mg/mL stock,
the exact nicotine volume is 0.006 mL. The calculator uses 0.01 mL, corresponding
to 10 mg/mL rather than 6 mg/mL.

Effects are more pronounced for small batches and low concentrations. Rounded
carrier splits can also cause ingredient-total discrepancies.

**Recommended fix:** Retain full internal precision and round display values
only. Define a practical minimum batch size or indicate when amounts fall
below useful measurement precision.

**Resolved (October 4, 2026).** Flavor amounts/weights, nicotine results, and
required PG/VG are now kept at full precision internally; components round
only when formatting output. A `formatMeasurement` helper marks positive
amounts that round to zero as `<0.01` so sub-precision doses are not shown as
zero. Regression tests cover the 0.1 mL example (6% nicotine rather than 10%)
and the sub-precision indicator.

### CALC-04 — Flavor-free recipes cannot be restored

**Priority:** Medium.

**Location:** `src/components/calculator/useCalculator.ts:141–142`.

Restoration requires `saved.flavors.length > 0`, treating valid empty flavor
lists as missing data.

**Reproduced:** Removing every flavor and remounting restores the default
5% flavor.

**Recommended fix:** Restore valid empty arrays.

**Resolved (October 4, 2026).** The restore path now accepts any valid flavors
array, including `[]`, instead of requiring at least one entry. A regression
test confirms a stored empty list is restored with no flavor rows.

### CALC-05 — Storage validation and error handling are incomplete

**Priority:** Medium.

**Location:** `src/components/calculator/useCalculator.ts:127–145, 244–258`.

Restoration trusts nicotine configuration and flavor objects without validating
fields or ranges. Writes have no error handling.

**Impact:** Malformed/old data can produce invalid results or runtime failures.
Storage denial or quota errors can disrupt calculator operation.

**Recommended fix:** Persist a versioned input-only draft, validate/migrate on
load, recalculate derived results, and handle storage failures gracefully.
Persisting derived weights and carrier amounts increases the possibility of
inconsistent restored state.

### CALC-06 — Newly added flavors ignore saved defaults

**Priority:** Medium.

**Location:** `src/components/calculator/useCalculator.ts:369–380`.

Add Flavor always uses 100% PG and 0% concentration, regardless of configured
flavor defaults.

**Recommended fix:** Keep loaded flavor defaults available to the add operation.
Clarify whether defaults describe all new flavors or only the initial row.

**Resolved (October 4, 2026).** Newly added flavors now use the loaded
settings' flavor percentage and PG/VG base, with derived amounts computed at
the current batch size. The decision is that defaults describe every new
flavor; guests and accounts without saved settings keep the neutral 100% PG /
0% flavor base. A regression test verifies the added row inherits the saved
percentage and ratio.

### CALC-07 — Invalid-recipe handling is inconsistent

**Priority:** Medium.

**Locations:**

- `src/components/calculator/useCalculator.ts:325–337`.
- `src/components/calculator/SaveRecipe.tsx:43–90`.
- `src/lib/models/recipe.ts`.

Controls can increase flavor percentages above 100 despite the HTML `max`.
Creation may reject values accepted by updates because update validation is
disabled. Impossible mixtures can be saved without distinguishing a usable
recipe from an invalid draft.

**Recommended fix:** Centralize validity and input constraints. Validate finite
numbers, percentages, PG/VG sums, and feasibility. Decide whether invalid drafts
are saveable and communicate that consistently.

## Styling findings

The four user-testing notes in `docs/todo.md` have identifiable causes, confirmed
in the Playwright follow-up. Fixes still require browser verification after
implementation.

### UI-01 — Heading font variable scope

`--font-display` is defined in theme scope using `--font-bebas-neue`, while
the Next font variable class is applied to `<body>`. The theme variable can
resolve before the referenced variable is available.

**Recommended fix:** Apply the Next font variable at the correct scope and/or
use Tailwind's inline theme-variable pattern.

**Locations:** `src/app/globals.css`, `src/app/layout.tsx`.

### UI-02 — Footer positioning on short pages

AppShell renders header/main/footer siblings without a viewport-height flex
layout.

**Recommended fix:** Use a full-height column layout with a growing main region,
keeping the footer in normal flow.

**Locations:** `src/components/layout/AppShell.tsx`, `src/app/globals.css`.

### UI-03 — Input border sizing

Old content-box sizing was copied into Tailwind's border-box reset. Text inputs
still use `width: calc(100% - 12px)`, exposing excess gradient inside wrappers.

**Recommended fix:** Rework sizing for border-box; review wrapper alignment and
numeric dimensions together.

**Locations:** `src/app/globals.css`, `src/components/ui/InputBorder.tsx`.

### UI-04 — Transparent link/button backgrounds

Global buttons receive a gradient background image. `bg-transparent` changes
only background color, so ostensibly transparent buttons retain gradients,
including on hover.

**Recommended fix:** Define explicit solid, gradient, and ghost variants
controlling both image and color. Centralize duplicated raw-button styling
through the shared button component.

**Locations:** `src/app/globals.css`, `src/components/ui/Button.tsx`, and usages
in Sidebar, auth forms, My Account, and InfoTooltip.

### UI-05 — Ingredient result-column alignment

**Locations:**

- `src/components/calculator/Ingredients.tsx:93–96`.
- `src/components/calculator/Flavor.tsx:67–74`.

The original grid used `justify-items: end` and a full-width first flavor-results
cell. Those rules were not fully carried over.

**Impact:** Percentages, volumes, and weights can lose their original
right-aligned column structure.

**Recommended fix:** Restore consistent result alignment and verify narrow phone
and desktop layouts.

### UI-06 — Footer logo collapses to zero size

**Priority:** Medium.

**Location:** `src/components/layout/Footer.tsx:10–17`.

The logo is absolutely positioned inside a flex child without a defined width.
Its containing block collapses to zero width. Tailwind's image `max-width: 100%`
then constrains the image to zero width despite its `w-[150px]` utility.

**Browser evidence:** At a 1280 px viewport, the image loaded successfully
(`naturalWidth: 107`) but its rendered bounding box was 0 × 0 px. Its parent
also had zero width. The desktop screenshot showed no footer logo.

**Recommended fix:** Give the logo container an explicit responsive width and
prevent unwanted flex shrink, or keep the image in normal flow. Verify that
it fits alongside footer links on narrow screens.

### UI-07 — Content lists have lost bullets and numbering

**Priority:** Medium.

**Location:** `src/app/globals.css:78–92` and content pages using lists.

Tailwind Preflight resets list styles to `none`. The ported global `ul` and
`ol` rules restore padding and spacing but not markers.

**Browser evidence:** Contribute's feedback-question list and Privacy Policy's
ordered list both compute to `list-style-type: none`, including their list
items. The original application retained browser-default markers.

**Recommended fix:** Restore disc/decimal markers for content lists while
preserving explicit `list-none` for menus and recipe lists. Check wrapped-item
indentation on mobile.

## Accessibility

### A11Y-01 — Labels, keyboard controls, and focus management

Concrete issues include:

- Calculator inputs and several account/auth inputs lack explicit accessible
  labels.
- Number controls use Increase/Decrease labels without identifying the field.
- Closed sidebar links/buttons remain keyboard-focusable despite `aria-hidden`.
- Sidebar and confirmation dialogs lack focus trapping/restoration.
- Confirmation dialogs lack accessible names and Escape handling.
- Recipe sorting uses clickable spans rather than keyboard-operable controls.
- Primary headings generally start at `<h3>` without a clear heading hierarchy.

**Recommended fix:** Add contextual labels, button semantics, inert handling for
closed UI, and accessible dialogs. Include keyboard checks with visual checks.

### A11Y-02 — Secondary text has insufficient contrast

**Priority:** Medium.

**Locations:** `src/app/globals.css`, calculator labels, and
`src/components/layout/Footer.tsx:20–25`.

Computed-color checks found:

| Text | Foreground/background | Contrast ratio |
| ---- | --------------------- | -------------- |
| Calculator Base label | `#6272a4` / `#21222c` | 3.36:1 |
| Footer legal links | `#414558` / `#15171b` | 1.89:1 |

Both are normal-sized text, below the WCAG AA 4.5:1 requirement. Footer links
are especially difficult to read in the screenshot. These palette choices
were inherited from the original application.

**Recommended fix:** Introduce readable secondary-text tokens or lighten these
usages, retaining the dark palette. Test normal, hover, focus, and disabled
states rather than globally changing a color also used for borders/backgrounds.

## Data integrity and API behavior

### DATA-01 — Account deletion leaves saved settings

**Location:** `src/app/api/user/route.ts:57–63`.

Deletion removes recipes and the user but leaves settings, despite the dialog
promising their deletion.

**Recommended fix:** Delete associated settings and make the operation robust
against partial failure. Existing orphaned records may need separate cleanup.

**Resolved (October 4, 2026).** Account deletion now removes recipes and saved
settings together (in parallel) before deleting the user, so a partial failure
leaves the account and a retry intact. Regression tests cover the successful
path and the failure path. Orphaned settings left by older deletions are not
cleaned automatically; they can be removed in a one-off database cleanup.

### DATA-02 — Recipe-title uniqueness is incomplete

**Locations:**

- `src/app/api/recipes/route.ts:31–43`.
- `src/app/api/recipes/[id]/route.ts:31–48`.
- `src/lib/models/recipe.ts:27–31`.

Creation checks before schema trimming, allowing whitespace variants to bypass
the check. Updates do not check duplicates; concurrent creates can both pass.

**Recommended fix:** Normalize consistently and enforce intended per-user
uniqueness in the database. Inspect existing duplicates before adding an index.

**Inspection pending:** the read-only `scripts/inspect-duplicates.mjs` reports
normalized per-author title duplicates, duplicate settings documents, and
mixed-case email data. Run it against staging/production and share the output
before adding indexes.

### DATA-03 — Duplicate settings documents are possible

**Locations:** `src/app/api/settings/route.ts:28–37`,
`src/lib/models/settings.ts`.

Find-then-create can race, and `user` lacks a unique index.

**Recommended fix:** Enforce one settings document per user and use an atomic
upsert after checking existing data.

**Inspection pending:** covered by `scripts/inspect-duplicates.mjs` (duplicate
settings documents per user). Atomic upsert and a unique index can follow
once the data is verified.

### API-01 — Malformed JSON produces a server error

**Location:** `src/lib/api.ts:16–32`.

A malformed signup request returned 500 rather than 400 in the local smoke
check.

**Recommended fix:** Separate request parsing/validation failures from unexpected
server failures. Translate duplicate-key errors into appropriate client responses.

**Resolved (October 4, 2026).** `handleApiError` maps malformed request JSON
(SyntaxError) to a 400 `Invalid JSON body.` response and MongoDB duplicate-key
failures (code 11000) to 409 `That value already exists.` Regression tests
cover the error mapping plus malformed-body and duplicate-key requests through
the signup route.

## Resilience and maintainability

### REL-01 — Authentication failures can look like success

**Location:** `src/components/providers/AuthProvider.tsx:60–80`.

`refresh()` suppresses failures and resolves after setting the user to null.
Login/signup callers can continue success paths when session retrieval failed.
Logout clears local state even if server-cookie clearing failed.

**Recommended fix:** Distinguish unauthenticated, transient failure, and successful
logout states. Propagate failures needed by callers.

**Resolved (October 4, 2026).** `refresh()` now treats only a 401 as signed
out; other failures are rethrown after logging. `logout()` still clears local
state but rethrows server failures. Callers handle the distinction: login and
signup already surface refresh errors, and Sidebar/My Account clear local
state and navigate even when the logout request fails. Regression tests cover
the 401 path, propagated refresh failure, and logout failure.

### REL-02 — Recipe-loader state is not reset on ID changes

**Location:** `src/components/recipes/RecipeLoader.tsx:15–39`.

The effect fetches a changed ID without resetting loading, recipe, or errors.
When the same instance receives another ID, the old recipe can remain visible
during loading and a previous error can persist after success.

**Recommended fix:** Reset request state on ID changes and model loading,
error, and data together.

**Resolved (October 4, 2026).** `RecipeLoader` remounts its request state via
a keyed inner component, so a changed ID starts fresh: no previous recipe or
error can linger while the new recipe loads. Regression tests cover the ID
change and error-clearing paths.

### MAINT-01 — Database module lacks its documented server-only marker

`src/lib/db.ts` lacks `import "server-only"`, required by project conventions.

**Resolved (October 4, 2026).** The marker was added to `src/lib/db.ts`.

### MAINT-02 — Profile-picture selection can fall back to an invalid URL

My Account and UserProfile can choose `"#"` as an image source while another
linked provider's picture exists. Select an available picture consistently
or omit the image.

**Resolved (October 4, 2026).** Both components now use the first available
picture (Google, then Twitter), label it with the provider it came from, and
omit the image entirely when neither exists. Regression tests cover the
fallback, preference, and omission cases.

### MAINT-03 — Summary views fetch full recipe documents

Recipe lists and account summaries fetch complete recipes where summary
projections or a count would suffice.

### MAINT-04 — Extract pure calculations and reduce derived state

A pure calculator function would simplify verification. Persisting only inputs
and deriving results would reduce state synchronization and restoration risks.

## Browser follow-up — October 4, 2026

### Method

Playwright MCP ran against the local production build on port 3100, using
desktop viewports of 1280 × 886/900 and narrow layouts at 390 and 320 px wide.
The browser reported Firefox-style platform font fallbacks and console output;
this was a single-browser pass, not cross-browser certification.

Checks covered the calculator, expanded nicotine configuration, Help, About,
Contribute, Privacy Policy, sidebar login UI, Settings, and My Account's
account-deletion confirmation. Authenticated Settings and My Account used
intercepted API responses with fixture data. Mutation requests were blocked
by the interceptor. No real account was created, modified, or deleted.

### Previously reported issues confirmed

| Issue | Browser evidence |
| ----- | ---------------- |
| UI-01: heading font | Headings computed to the system sans-serif family, not Bebas Neue. The theme display token was empty while the body font variable existed. The console also warned that the preloaded font was unused. |
| UI-02: footer position | On Help at a 900 px viewport height, the footer ended at approximately 832 px, leaving roughly 68 px below it. |
| UI-03: input border | Sidebar email input measured 202 px inside a 218 px wrapper, leaving an 8 px right inset. Flavor-name input also exposed excess gradient on the right/bottom rather than a uniform 2 px border. |
| UI-04: transparent buttons | Sidebar Back/Close and login text buttons had transparent background color but retained a purple/cyan gradient background image. |
| UI-05: result alignment | Ingredient grids computed `justify-items: normal`; the flavor volume appeared at the far left rather than aligned with other volume results. |
| A11Y-01: closed sidebar | Tabbing past footer links reached Close Menu, the home link, and menu links while the sidebar had `aria-hidden="true"` and was offscreen. |
| A11Y-01: confirmation dialog | Opening account deletion left focus on the trigger outside the dialog. Escape did not dismiss it. Tabbing past Cancel/Delete moved to background footer links while the dialog remained open. |

### Additional findings

- UI-06: the footer logo loaded but rendered at 0 × 0 px.
- UI-07: content lists lost bullets and numbering through the reset.
- A11Y-02: calculator labels and footer links fell below normal-text contrast
  requirements.

### Checks that did not reveal additional failures

- The default calculator did not produce horizontal page overflow at 390 or
  320 px widths.
- Mock-authenticated Settings did not produce horizontal overflow at 320 px.
- Sequential typing of `0.5` in a flavor percentage field worked in this browser.

These observations do not establish that every expanded configuration, long
flavor/recipe name, device, or browser fits correctly. Real OAuth, email, and
database-backed mutation flows remain unverified end to end.

## Overall assessment

Consolidation into one Next.js app is sensible. Shared types, the API wrapper,
cookie-based sessions, owner checks, static informational pages, and a small
database pool provide good foundations. Build and production dependency checks
are healthy.

The main weakness is that legacy behavior was preserved too literally,
carrying forward security flaws, fragile calculator initialization, and CSS
assumptions that no longer fit Tailwind's reset. Focused fixes can substantially
improve the project without another rewrite.
